# 07. オフライン同期設計

iPhoneから使うときに、ネットワークが切れていてもWikiを読めるようにするための設計。端末にライブラリのコピーを保持し、LANに復帰したらサーバーと同期する。

本章の範囲は**オフライン閲覧まで**とする。オフライン編集は7.9に理由と将来の接続点のみ記す。

## 7.1 前提となる実測値

方式の判断は本番ライブラリの実測(2026-09-13)に基づく。

| | 件数 | 合計 | 平均 |
|---|---|---|---|
| Markdown | 1,887 | 2.5 MB | 1.4 KB |
| 添付 | 376 | 415 MB | 1.1 MB |

Markdownはライブラリ全体の0.6%しかない。**部分同期のような仕組みを入れる理由がない**ため全件を端末に持つ。容量を占めるのは添付のみであり、ここだけを遅延取得の対象とする。

なお添付のリサイズ(#247・#248)が入ると平均200KB前後まで下がる見込みで、その場合376件でも75MB程度となり、実質的に添付も全件が端末に収まる。

## 7.2 全体方針

| 論点 | 決定 | 理由 |
|---|---|---|
| Markdownの保持範囲 | **全件ミラー** | 2.5MBであり部分同期の複雑さに見合わない。オフライン検索・wikilink解決が素直に実現できる |
| 添付の保持範囲 | **遅延取得+LRUキャッシュ** | 415MBは端末に置けない |
| 正本(source of truth) | **サーバー** | 端末は完全なコピーを持つが正本ではない(7.3) |
| 同期の単位 | 文書単位 | 文書は平均1.4KBで、部分差分を取る意味がない |
| 同期の起点 | マニフェスト突合(7.4) | 削除・外部変更・mtime巻き戻しを一つの仕組みで扱える |

## 7.3 なぜサーバーを正とするか

Obsidianは端末を正とし、競合時は両方を残す。同じ方式を採らない理由は、tsumiwikiが**サーバー側に正本を持つ機能をすでに備えている**ためである。

| サーバー側の機能 | 端末を正にした場合の破綻 |
|---|---|
| 編集ロック(`locks` / FR-LOCK) | オフライン中はロックを保持できず、ロックの意味が失われる |
| 保存ごとのGitコミット(06章) | まとめてpushしたコミットの著者と時刻が実際の編集と乖離する |
| FTS5インデックス | 端末側の更新がインデックスに反映される順序を保証できない |
| 複数人での編集 | 後勝ちで他人の編集が消える |

Obsidianが端末を正にできるのは、サーバー側にロックも履歴の正本も持たないためである。tsumiwikiは「**端末に全部ある**」というObsidianの利点だけを採り、「端末が正」は採らない。この二つは独立した選択であり、両立しない理由はない。

## 7.4 同期プロトコル

### 7.4.1 方式: マニフェスト突合

更新日時カーソル(`since`)による差分取得ではなく、**全文書のパスと更新日時の一覧(マニフェスト)を取得し、端末側で突合して必要な文書だけ本文を取りに行く**方式とする。

カーソル方式を採らない理由:

- `doc_index.updated_at` はファイルのmtimeであり、**外部からのファイルコピーやObsidianの操作でmtimeが過去に巻き戻ることがある**。カーソル方式ではこれを取りこぼす
- `doc_index` には削除の記録(tombstone)が無く、削除の検出には結局パス一覧の突合が必要になる。tombstoneテーブルを足す案もあるが、「DB喪失時もライブラリから再構築可能」(要件05章5.4)という原則に、ライブラリ側に存在しない情報を持ち込むことになる
- 同一 `updated_at` の文書が複数あるとページング境界で取りこぼすため、カーソルを `(updated_at, doc_path)` の複合にする必要があり、かえって複雑になる

マニフェストは1,887件で約110KB(gzipで25KB程度)。これを毎回取得するコストは、**ETagによる304応答**で解消する(7.4.3)。

### 7.4.2 エンドポイント

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/sync/manifest` | 全文書の `[{path, updatedAt, size}]` と `count`。`ETag` を返す |
| POST | `/api/sync/docs` | `{paths: [...]}` で指定した文書の本文を返す。`{docs: [{path, title, folder, updatedAt, tags, body}]}` |

`/api/sync/docs` が読み取りなのにPOSTであるのは、初回同期で1,887件のパスを渡す必要があり、GETのクエリ文字列では長さが足りないため。既存の作法どおり `X-Requested-With: TsumiWiki` を必須とする。

- 1リクエストあたりの `paths` の上限は200件とする。クライアントが分割して呼ぶ
- いずれも認証必須。未認証は `401`
- 入出力の型は `packages/shared/src/index.ts` にzodスキーマとして定義する

### 7.4.3 手順

**初回同期**

1. `GET /api/sync/manifest` → 全パスと更新日時、`ETag` を保存
2. 全パスを200件ずつに分割し `POST /api/sync/docs` で本文を取得してIndexedDBへ保存
3. 完了時に `lastSyncAt` を記録

1,887件・2.5MBで、200件×10回のリクエストになる。

**差分同期**

1. `GET /api/sync/manifest` に `If-None-Match: <保存したETag>` を付けて送る
   - `304 Not Modified` ならライブラリに変更なし。ここで終了(通常はこのパスを通る)
2. `200` の場合、返ってきたマニフェストとローカルの内容を突合する
   - **マニフェストにあり、ローカルに無い、または `updatedAt` か `size` が異なる** → 取得対象
   - **ローカルにあり、マニフェストに無い** → 削除する
3. 取得対象を `POST /api/sync/docs` で取得して保存
4. `ETag` と `lastSyncAt` を更新

リネームは「旧パスの削除 + 新パスの追加」として自然に処理される。

ETagは `doc_index` の内容(パス・更新日時・サイズの集合)から算出する。個々の文書の保存だけでなく、**外部変更の取り込み(`library-watcher` / `sync-service`)によるインデックス更新でも変化すること**を保証する。`size` を含めるのは、インデクサ自身が mtime(ms) と size の一致で unchanged 判定しており(設計02章2.3)、同一 mtime tick 内でサイズだけが変わる書き換えは `updatedAt` だけでは検知できないため。ETagの検出力が `doc_index` の更新判定より弱いと、`doc_index` は更新されたのにETagが同値のままとなり、端末が304を受けて変更に気づけない。

**この契約は端末側(#253)の突合条件にもそのまま及ぶ**: 上記の手順2のとおり、ローカルとの差分判定は `updatedAt` の一致だけでなく `size` の一致も見ること。ETag側だけ検出力を上げても、端末の突合が `updatedAt` のみだと「ETagが変わる→端末は取得対象なしと判断→ETagだけ更新して終わる」という形で古い内容のまま収束してしまう。

### 7.4.4 同期のトリガ

**iOSではPWAはバックグラウンドで動作しない。** ホーム画面から起動したアプリを離れると、JavaScriptの実行もタイマーも停止する。したがって「閉じている間に定期同期する」ことは原理的にできず、**同期は前面に戻ってきた瞬間に行うのが主軸**になる。定期ポーリングはアプリを開いたままにしている間の保険でしかない。

| トリガ | 契機 | 備考 |
|---|---|---|
| `visibilitychange`(visible) | **アプリを開いた・他アプリから戻った** | 主軸。iOSで確実に発火する |
| `pageshow`(`persisted`) | サスペンドやbfcacheからの復帰 | 主軸。`visibilitychange` が出ない復帰経路を拾う |
| `online` | **Wi-Fiに接続した** | ネットワーク復帰。到達性は別途判定(後述) |
| アプリ起動時 | 初回読み込み | |
| 定期ポーリング | 既定5分 | 前面にある間のみ。開きっぱなしの場合の保険 |
| 手動同期 | ユーザー操作(7.7) | |

ETagによる304応答(7.4.3)で変更が無いときの通信が数百バイトで済むため、**前面復帰のたびに同期しても負荷にならない**。これが「復帰イベントを主軸にする」設計を成立させている。

採用しない手段:

| 手段 | 理由 |
|---|---|
| Background Sync API | Safari未対応 |
| Periodic Background Sync API | Chrome/Android のみ。Safari未対応 |
| Network Information API | Safari未対応 |
| Web Push によるサーバーからの起床 | iOS 16.4以降で可能だが、**Appleのプッシュサーバーを経由するためLAN内だけでは届かない**。社内LAN運用を前提とする本システムには合わない |

**多重実行の防止**: 実行中フラグで排他する。`visibilitychange` と `online` と `pageshow` は復帰時に同時に発火しうるため、同期は1本しか走らないことを保証する。あわせて**最小間隔(10秒)を設け**、短時間にアプリを何度も往復しても同期が連発しないようにする。

**到達性の判定**: `navigator.onLine` は「ネットワークに繋がっているか」しか分からず、**サーバーに到達できるかは別問題**(LAN外にいる場合など)。マニフェスト取得自体をタイムアウト付き(3秒)で行い、その成否を到達性の判定として扱う。疎通確認専用のエンドポイントは設けない。

**失敗時**: 静かにオフライン扱いへ移行する。エラートーストを出し続けない。部分的に取得できた文書は保持してよいが、**ETagは全件の取得が完了したときにのみ更新する**(途中で失敗した状態をもって「同期済み」としない)。

## 7.5 ローカルストア(IndexedDB)

DB名 `tsumiwiki-offline`。localStorageは容量が足りないため使わない(タブ状態・テーマ等の既存の設定用途はそのままでよい)。

| ストア | キー | 内容 |
|---|---|---|
| `docs` | `path` | `{path, title, folder, updatedAt, size, tags, body}`。インデックス: `folder` / `updatedAt` |
| `attachments` | `relPath` | `{relPath, size, cachedAt, lastAccessAt}`。実体はCache Storageにあり、本ストアはLRU判定用の索引 |
| `meta` | `key` | `userId` / `manifestEtag` / `lastSyncAt` / `schemaVersion` |

- IndexedDBへのアクセスは1モジュールに集約し、UIから直接触らない
- `schemaVersion` を持ち、将来スキーマを変えたときは**移行せず全件を捨てて再同期する**。正本はサーバーにあり、2.5MBの再取得は数秒で終わるため、移行コードを書く価値がない

## 7.6 Service Worker

| 対象 | 戦略 |
|---|---|
| app shell(Viteのビルド成果物) | プリキャッシュ。ビルド時に生成されるマニフェストを使う(ファイル名にハッシュが付くため手書きの一覧は持たない) |
| ナビゲーション | ネットワーク優先、失敗時はプリキャッシュした `index.html` を返す |
| `/api/files/*` `/api/embed`(添付) | キャッシュ優先 + LRU(7.8) |
| その他の `/api/*` | **キャッシュしない**。ネットワークへ素通し |

APIをキャッシュしない理由: 文書データのオフライン提供はIndexedDBの責務であり、Service Workerが古いAPIレスポンスを返すとログイン状態や認可の判定が壊れる。**401/403をキャッシュしたり、キャッシュで肩代わりしたりしてはならない**。

実装は `vite-plugin-pwa` の `injectManifest` 方式を用いる(キャッシュ戦略を自前で記述するため)。

**更新の配り方**: 新しいバージョンを検知したら通知を出し、ユーザーの操作で再読み込みする(即時の `skipWaiting` は行わない)。オフライン編集を将来入れたときに、編集中のタブが無警告で置き換わるのを避けるため。

**配信側の注意**: 本番ではFastifyがビルド成果物を静的配信する(単一ポート運用、01章1.4)。`sw.js` が**ルートスコープ**で、正しい `Content-Type` と、キャッシュされない `Cache-Control` で返ることを確認する。

## 7.7 同期ステータスの表示

| 状態 | 意味 |
|---|---|
| 同期済み | サーバーに到達でき、最新の状態 |
| 同期中 | 同期処理の実行中 |
| オフライン | サーバーに到達できない(端末のデータで動作中) |

- 最終同期日時を表示する
- 手動同期の導線を設ける
- 初回同期は全件取得で時間がかかるため進捗を表示する
- **オフラインであることが、編集できない理由として伝わる表示にする**。アイコンだけで終わらせない
- ポーリングのたびに「同期中」が一瞬表示されて消える、というちらつきを起こさないこと。304で終わった同期は状態を変えない

## 7.8 容量設計

| 項目 | 値 |
|---|---|
| Markdown | 全件(上限なし)。2.5MB |
| 添付キャッシュ上限 | 既定200MB(設定で変更可) |
| 追い出し方針 | LRU(`attachments.lastAccessAt` の古い順) |

- 上限は#247・#248のリサイズ結果を見て最終決定する。平均200KBまで下がれば376件で75MB程度となり、全件が収まる
- 一度も取得していない添付をオフラインで開いた場合は、**壊れた画像アイコンではなく意味の分かる代替表示**にする
- 設定画面からストレージ使用量を確認でき、手動で全消去できる導線を設ける

## 7.9 オフラインでできること・できないこと

| 操作 | オフライン |
|---|---|
| ツリー表示・文書閲覧 | ○ |
| タグ絞り込み・全文検索 | ○(7.10) |
| wikilink の解決と遷移 | ○ |
| 取得済み添付の表示 | ○ |
| 編集・新規作成・移動・削除 | **×** |
| 履歴・差分・復元・ごみ箱 | **×** |
| ユーザー管理・ライブラリ設定 | **×** |

- ローカルとサーバーのどちらを見ているかの判定は**1箇所に集約**する。画面ごとに個別に判定しない
- できない操作は**無効化して理由を示す**。押せてしまってエラーになる、無反応になる、という状態を残さない

**オフライン編集を本フェーズの範囲外とする理由**は7.3のとおり、競合解決の設計がロック・Git履歴と絡んで重く、閲覧の実現を遅らせるためである。将来入れる場合の接続点を記しておく。

- 端末に編集キュー(outbox)を持ち、復帰時に既存の `PUT /api/docs` へ順に送る
- 競合検知は**既存の `baseUpdatedAt` による楽観ロックをそのまま使う**。不一致は `CONFLICT` が返る(03章)
- 競合時はObsidianと同様に**両方を残す**(競合コピーを別ファイルとして作成し、解決UIへ誘導する)
- オフライン中はロックを取得できないため、オフライン編集はロックの外側での楽観更新になる。この位置づけを明示すること

## 7.10 オフライン全文検索

オンラインの検索はサーバーのFTS5(trigram)で行っている(03章)。オフラインではローカルストアのデータで検索する。

- 全文が2.5MBしかないため、**まず素朴な実装(全件走査)で速度を実測し、足りなければ索引を検討する**。最初から索引ライブラリを導入しない
- 日本語が正しく検索できること。サーバーのtrigramと**結果の傾向が大きくずれないこと**(部分一致が効き、単語の区切りに依存しない)
- 検索結果の表示(ヒット箇所の抜粋・ハイライト)をオンライン時と揃える
- UIをブロックしないこと。件数によってはWeb Workerへの退避を検討する

## 7.11 セキュリティ

| 項目 | 方針 |
|---|---|
| ログアウト | **IndexedDBと添付キャッシュを完全に破棄する**。app shellのキャッシュは残してよい |
| ユーザー切替 | `meta.userId` が不一致ならローカルデータを全件破棄してから同期する |
| セッション失効(401) | ログイン画面へ遷移する。ローカルデータは破棄しない(同一ユーザーの再ログインが大半のため)。再ログイン時に `userId` を照合する |
| オフライン時の閲覧 | セッションの有効性を確認できないため、**最後にログインしたユーザーとして閲覧を許す** |
| 共用端末 | 上記により端末に本文が残る。使い終わったらログアウトする運用をマニュアルに明記する(#258) |

**iOSのストレージ退避について**: script-writableストレージの7日で削除される制限は、Safariでのブラウジングが対象であり、**ホーム画面に追加したPWAは対象外**である。ただしストレージ逼迫時の退避と、ユーザーがPWAを削除した場合の消失は起こりうる。端末は正本ではないため、消えても再同期すればよい(2.5MBの再取得で復旧する)。
